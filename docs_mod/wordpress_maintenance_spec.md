# KIS-2026-Base - WordPress サイトの保守

本資料では、クラシックテーマからブロックテーマに移したとき、管理と保守のどこが楽になり、何が残るかをまとめます。

本資料は営業スタッフ向けの説明資料です。開発者向けの個別仕様は [`docs/SPEC.md`](../docs/spec.md) です。

記録日は2026-10-01です。
2026-10-02に、「情報源」「バックアップとローカル環境」「ユーザー権限と公開前チェック」の章を足しました。
2026-10-02に、第6章へメディアファイルの節を足しました。

## 1. この資料について

### 1.1. 目的

公開中のサイトは、クラシックテーマ `kix` でできています。今後はブロックテーマに移します。

この資料は、移したあとに「どの作業が管理画面で済むようになるか」と「どの作業が残るか」を説明します。テーマのプログラム仕様そのものは書きません。

### 1.2. 読む人

普段、WordPress のテーマやプラグインを開発しない人を想定しています。営業スタッフが、サイトの更新依頼と本番作業の境界を判断するための資料です。

### 1.3. 対象のサイト

関西総合システムの Web サイトです。3つの段階があります。

| 段階 | 名前 | 状態 |
| --- | --- | --- |
| いまの公開サイト | クラシックテーマ `kix` | 表示の骨組みがテーマのファイルにある |
| 移行の作業用 | `kis2026_base` | ブロックテーマに移すための土台。PHP のテンプレートはまだ残っている |
| 移行後 | ブロックテーマ | 見た目はサイトエディター。記事の種類とフォームはプラグイン |

`kis2026_base` は、移行が終わった状態ではありません。いまの管理画面に、サイトエディターの操作は出そろっていません。

### 1.4. この資料に書かないこと

下記は、別の資料です。

* 各ページの掲載文と画面レイアウト
* サーバー契約、DNS 切替、メール設定の手順
* 開発者向けのファイル構成

## 2. どこを変えると、何が変わるか

クラシックテーマが劣り、ブロックテーマが優れる、という比較ではありません。変える場所が違います。確認する場所も違います。

`kix` では、管理画面の入力だけでは届かない表示があります。ヘッダー、フッター、トップページのボタンは、テーマのファイルにリンクが書いてあります。WordPress のメニュー画面だけでは直せません。

| 変えたい内容 | クラシックテーマ `kix` | ブロックテーマに移したあと |
| --- | --- | --- |
| ヘッダーとフッターのリンク | テーマのファイルを開発者が直す | サイトエディターで直せる |
| 電話番号などの共通表示 | テーマのファイルを開発者が直す | テンプレートパーツで直せる |
| ページ共通の並び | ページ種別ごとの PHP テンプレートに依存する | テンプレートとパターンで組む |
| 色と文字の共通設定 | ページ別の CSS ファイルを開発者が直す | サイト全体のスタイルで直せる範囲が広がる |
| ニュースや導入事例の本文 | 管理画面で入力する | 管理画面で入力する |
| イベント日付や写真の入力欄 | 追加の入力欄とテーマの表示が対になっている | 入力欄は残る。置き場所はプラグインに寄る |
| 問い合わせフォーム | テーマとフォーム用プラグインが組になっている | 別のプラグインに置き換わる |
| WordPress やプラグインの更新 | 更新後に表示を確認する | 更新後に表示を確認する |

移行後も、本文の入力は管理画面です。楽になるのは、サイト全体に効く見た目と、共通パーツの変更です。

## 3. 楽になること

### 3.1. ヘッダーとフッター

`kix` のフッターには、下記がファイルにハードコーディングされてあります。

* 資料請求とお問い合わせのボタン
* 電話番号
* 製品、導入事例、会社情報、採用、方針ページへのリンク

文言やリンクを1つ変えるときも、開発者がテーマのファイルを直します。直したあとは、サイト全体の表示確認が必要です。

ブロックテーマでは、ヘッダーとフッターをテンプレートパーツとしてサイトエディターで扱います。リンクの追加、電話番号の変更、ボタン文言の変更は、ファイルを開かずに直せる範囲が広がります。

直した内容はサイト全体に出ます。本番で保存する前に、確認用の環境で見る運用は残します。

### 3.2. ページの骨組み

`kix` では、トップ、ニュース、イベント、導入事例、問い合わせなどで、表示用の PHP ファイルが分かれています。一覧の並び、ボタン、英語見出しの有無は、そのファイルが決めています。

営業スタッフが管理画面で直せるのは、主にタイトルと本文です。並びや共通ボタンを変える依頼は、開発者の作業になります。

ブロックテーマでは、その骨組みをテンプレートとパターンにします。繰り返し使う塊をパターンにしておけば、同じ塊をページに置けます。新しいページ種別をゼロから足す作業は、引き続き開発者です。

### 3.3. 色と文字

`kix` では、ページの種類ごとに CSS ファイルが分かれています。トップだけ、イベントだけ、という直しがファイル単位になります。直しの影響範囲は、ファイル名からは読み取りにくいです。

ブロックテーマでは、色、文字、間隔の共通指定をサイト全体のスタイルにまとめます。サイト全体のトーンをそろえる変更は、ここを直します。特定のブロックだけを変えるときは、そのブロックの設定を見ます。

フォントをサイト全体で入れ替えるような変更は、スタイル側の作業です。記事本文の文字を打ち替える作業ではありません。

### 3.4. テーマと機能を分ける

`kix` のテーマの中には、表示以外のしくみも入っています。

* 「イベント」と「導入事例」という、記事の種類
* 「ニュース」という管理画面上の表示名
* 「問い合わせ」フォームの初期値
* 計測タグや、一部ページの説明文

テーマを更新すると、これらの動きも一緒に影響を受けます。管理画面を見ただけでは、どこがテーマ依存か分かりません。

移行後のテーマは、見た目に担当を限定します。記事の種類、フォーム、方針ページの台帳はプラグインが持ちます。見た目の依頼と、記事の種類を増やす依頼を、分けて出せます。

営業スタッフがプラグインを作るわけではありません。依頼先と確認場所が分かれる、という意味で保守が楽になります。

### 3.5. 問い合わせフォーム

いまのフォーム用プラグインは、開発元の保守が止まっています。テーマ側にも、フォームの初期値を決める処理があります。この組のまま長く置くことが、保守上のリスクです。

移行では、フォームを別のプラグインに置き換えます。置き換え自体は開発者の作業です。置き換えたあとは、項目のラベルや並びを管理画面で直せる範囲が広がります。

送信先の変更、自動返信の文面、個人情報の項目追加は、届き先と保存場所の確認が必要です。画面上のラベル変更だけで終わらせません。

## 4. 変わらないこと

ブロックテーマにしても、次は残り続けます。

| 項目 | 移行後も同じこと |
| --- | --- |
| ログインとユーザー | WordPress のアカウントで入る。権限の考え方は残る |
| 権限と公開前の確認 | 毎日のアカウントと管理者を分ける。確認はサイト全体と記事で分かれる。詳細は第7章 |
| 文章と画像 | ニュース、導入事例、採用、会社情報は、管理画面で更新する |
| 画像と PDF | ライブラリの登録とファイルの両方を残す。詳細は第6章 |
| 記事の種類 | イベント、導入事例、製品などは残る。メニュー名はプラグイン側に移る |
| 問い合わせ | 届くこと、返信すること、送信テストをすることは残る |
| 個人情報 | 取得項目と利用目的の確認は残る。保護方針の文章確認も残る |
| 方針ページ | 個人情報の保護方針と、情報セキュリティ基本方針は公開し続ける |
| 更新作業 | WordPress 本体、プラグイン、PHP の更新後に、表示とフォームを確認する |
| 更新の知らせ | 管理画面の「更新」と、公式の告知で知る。詳細は第5章 |
| 本番の変更 | 確認していない見た目の変更を、本番に直接出さない |
| インフラ | サーバー、ドメイン、SSL 証明書、バックアップはテーマの種類と無関係 |
| バックアップと試作 | 戻すためのコピーと、公開前のローカル試作は残る。詳細は第6章 |
| 計測 | アクセス計測のタグは、テーマ方式を変えても、確認対象のまま残る |
| 新しい機能 | ページ種別の追加、外部サービスとの接続は、開発者の作業 |

「一度移行すれば、更新ボタンを押すだけで安全」…には、なりません。更新のあとで、主要ページとフォームを、目で見る作業は残します。

## 5. 信頼できる情報源に関わり続ける

更新の有無は、検索結果や個人のブログではなく、決まった場所で見ます。関わり続けるとは、毎日すべてを読むことではありません。同じ場所を、決めた間隔で開くことです。

テーマをブロックテーマに変えても、この見方は変わりません。

### 5.1. このサイトで最初に開く画面

管理画面の「ダッシュボード」、その中の「更新」を開きます。ここに、このサイトに適用できる、新しいバージョンが並びます。

* WordPress 本体
* プラグイン
* テーマ
* 翻訳

並んでいることは、「新しいバージョンがある」という知らせです。本番サイトで更新ボタンを押す作業ではありません。名前と件数を控え、開発者に渡します。本番への反映は、第8章の依頼に含めます。

`kix` は、公式ディレクトリで配っているテーマではありません。社内で直したテーマは、「更新」のテーマ欄に出ません。この欄に名前がないテーマもあります。それは安全のサインではありません。

保守の止まったプラグインは、新しい版がないので並びません。第3.5節のフォーム用プラグインが、その例です。

### 5.2. 公式の告知

WordPress 本体のリリースや、広く注意する告知は、公式の Slack に出ます。参加には WordPress.org のアカウントが必要です。入口は [Make WordPress の Slack 案内](https://make.wordpress.org/chat/) です。

まず見るチャンネルは `announcements` です。セキュリティに関する告知を見落とさないための場所です。

日本語のチャンネルは下記です。

* [ja](https://wordpress.slack.com/archives/C0BA1EZ0S2U)
* [ja-community](https://wordpress.slack.com/archives/C0B992ZQR3K)
* [ja-docs](https://wordpress.slack.com/archives/C0B9ARKHWAY)
* [ja-requests](https://wordpress.slack.com/archives/C0B9ARYJ160)

Slack は、WordPress の制作に関わる人の連絡場所です。操作に困ったときの相談窓口ではありません。サイトの不具合は、第8章のとおり開発者に依頼します。

ログインせずにリリースの告知を読むなら、[WordPress 日本語のニュース](https://ja.wordpress.org/news/) を開きます。

### 5.3. 日本語で顔を合わせる集まり

「更新」の一覧だけでは、そのバージョンが自社サイトにどう効くかは分かりません。日本語で話を聞ける集まりに、時々出ると、告知の読み方が身につきます。

参加の申し込みは Meetup で行います。アプリは、Meetup [iOS/iPadOS 向け](https://apps.apple.com/jp/app/meetup-ソーシャルイベントとグループ/id375990038) または [Android 向け](https://play.google.com/store/apps/details?id=com.meetup) です。

関西と、その近隣で続いている集まりは、下記です。

* [Kansai WordPress Meetup](https://www.meetup.com/kansai-wordpress-meetup/) は、関西の集まりです。対象には大阪、兵庫、京都が含まれます (関西の場合は、大阪市と神戸で、おおむね月2回開催)。滋賀と奈良も含みます。初めての人でも参加できます。
* [Kagawa WordPress Meetup](https://www.meetup.com/kagawa-wordpress-meetup/) は、香川の集まりです。関西の外ですが、日本語で続いている集まりです。

集まりは、学びの場です。本番サイトの更新ボタンを、その場の話だけで押す場所ではありません。

### 5.4. 見る間隔

* 月に1回、「ダッシュボード」の「更新」を開く
* 並んでいた項目の名前を、開発者に渡す
* セキュリティの告知が出た週は、月1回を待たずに渡す
* Meetup への参加は、年に数回で足りる

## 6. バックアップ、メディア、ローカルでの試作

ブロックテーマにしても、戻すためのコピー、メディアの扱い、公開前に試すコピーは残ります。

### 6.1. 何を残し、いつ残すか

バックアップは、本番が壊れたときに戻すためのコピーです。取る中身と、取る間隔は、別の話です。

| 呼び方 | 意味 |
| --- | --- |
| フル | データベースとファイルの両方。記事、設定、画像、テーマ、プラグインを含む |
| データベース | 記事、固定ページ、設定、フォームの記録。画像そのものは含まない |
| ファイル | 画像、テーマ、プラグイン。記事の本文はデータベース側にある |
| Daily | 毎日取る、という間隔。中身の種類ではない |
| Monthly | 毎月取る、という間隔。中身の種類ではない |

Daily や Monthly という名前は、中身の種類を表しません。データベースを毎日取り、ファイルを毎月取る、という組み合わせが、コミュニティではよく紹介されます。記事は毎日変わり、画像やテーマは容量が大きいためです。

コピーの保管先は、本番サーバーの中だけにはしません。サーバーごと止まったときに、戻す元が一緒に消えるためです。保管先の例は Dropbox です。毎日のコピーを際限なく残すと、容量が足りなくなります。何世代残すかは、開発者が決めます。

フルは、WordPress の記事とファイルです。サーバー契約やドメインは含みません。

この作業の候補は、[UpdraftPlus](https://ja.wordpress.org/plugins/updraftplus/) です。間隔を決めて取り、Dropbox に置けます。壊れた本番を戻す操作も、このプラグインから行います。

戻す操作は、本番のいまの中身を、過去のコピーで置き換えます。営業スタッフが押すボタンではありません。

### 6.2. メディアは、登録とファイルの両方

「メディア」の「ライブラリ」にファイルを上げると、2つができます。

* ファイルそのもの。画像、PDF、動画が、サーバーのフォルダーに置かれる
* 登録。データベースに、ファイルの場所とタイトルが残る

ライブラリの一覧は、登録を見ています。登録だけ戻してファイルがないと、一覧には出ても、開くと画像がありません。ファイルだけ戻して登録が古いと、フォルダーにはあるのに、一覧からたどれません。

1枚上げると、表示用の小さい版も一緒に作られます。ファイルのコピーは、その小さい版も含みます。

データベースの Daily は、登録を毎日残します。画像そのものは含みません。ファイルの Monthly は、画像そのものを毎月残します。戻すときは、そろった時点の両方を使います。新しい登録に、古いファイルだけを重ねると、その間に上げた画像が欠けます。

戻したあとに見るのは、下記です。

* ライブラリの一覧に、問題の画像が出るか
* その画像を開いて、中身が表示されるか
* 記事のページで、同じ画像が出るか

一覧にあって中身がないときは、登録だけが戻っています。ページにあって一覧にないときは、ファイルと登録が食い違っています。どちらも、開発者にその違いを伝えます。自分で戻すボタンは押しません。

一部のロゴは、テーマのファイル側にあります。ライブラリの登録ではありません。`kix` にも、テーマ側の画像があります。ライブラリを戻しても、そちらは戻りません。

### 6.3. 画像の入れ方と、アドレスを変えない差し替え

記事や PDF は、ライブラリに上げます。パソコンのフォルダーに置いただけでは、サイトの登録にはなりません。

スマートフォンの写真は、そのままではサイズが大きいです。ページが重くなります。上げたときに圧縮し、必要なら WebP にする道具の候補は、[EWWW Image Optimizer](https://ja.wordpress.org/plugins/ewww-image-optimizer/) です。導入は開発者です。導入前に上げた大きい写真は、自動では縮みません。

同じ資料の新しい版を、これまでと同じアドレスで配りたいときは、新しいファイルを足すだけでは足りません。足すと、アドレスが変わります。古い記事や、印刷した URL は、古いファイルのままです。アドレスを変えずに中身を差し替える道具の候補は、[Enable Media Replace](https://ja.wordpress.org/plugins/enable-media-replace/) です。

SVG は、図形のファイルです。WordPress は初期状態では、ライブラリに普通の画像として出しません。出す道具の候補は、[SVG Support](https://ja.wordpress.org/plugins/svg-support/) です。SVG には、画像以外の動作を含むものがあります。出すかどうかは、開発者が決めます。

この3つは、戻すためのプラグインではありません。戻す作業は、登録とファイルの両方を、UpdraftPlus で戻すことです。

### 6.4. ローカルで新しい製品を試す

ローカル環境は、自分のパソコンの中で動く WordPress です。公開サイトの訪問者には見えません。新しい製品や、ブロックテーマの見た目を、ここで試します。

パソコンの中で WordPress を動かす道具には、下記があります。

* [Local by Flywheel](https://localwp.com/) は、いまの作業用サイトで使っています
* [Studio by WordPress.com](https://developer.wordpress.com/ja/studio/) は、同じ目的の別の道具です

本番の記事や設定をローカルに下ろすことと、ローカルの実験を本番に上げることを、リフトと呼びます。データベースを移す道具の候補は、[WP Migrate Lite](https://ja.wordpress.org/plugins/wp-migrate-db/) です。UpdraftPlus が戻すためのコピーなのに対し、こちらは環境の間でデータを移す道具です。

上げる操作は、本番の記事と設定を、ローカルの実験で置き換えます。確認していない実験を、そのまま上げません。

下ろしたコピーには、問い合わせと個人情報が入ります。社外のパソコンやメールでは配りません。

ローカルで保存した変更が、自動で本番に出ることはありません。出すときは、第8章の依頼にします。

### 6.5. 見るときの目印

* 試作のアドレスが、本番のドメインではないこと
* その試作を本番に出すかどうか
* Dropbox にバックアップが残っているかを、開発者に尋ねること
* 戻したあと、ライブラリの画像が開くこと

## 7. ユーザー権限と、公開前の確認

ブロックテーマにしても、誰が何をできるかは残ります。確認には、2つのタイミングがあります。サイト自体を公開する前と、公開後に記事を1本出す前です。

### 7.1. 毎日のアカウントと、管理者

WordPress のアカウントには、権限があります。権限ごとに、できることが違います。

| 権限 | 記事の公開 | プラグインやテーマ | ユーザーの追加 |
| --- | --- | --- | --- |
| 管理者 | できる | できる | できる |
| 編集者 | すべての記事と固定ページ | できない | できない |
| 投稿者 | 自分の記事だけ | できない | できない |
| 寄稿者 | できない。下書きまで | できない | できない |

寄稿者は、初期状態では画像をアップロードできません。写真付きの記事を自分で作る人は、投稿者以上が向きます。

毎日の記事の作成は、編集者または投稿者で行います。管理者では行いません。管理者は、プラグインの追加、WordPress の更新、ユーザーの追加に限って使います。

macOS では、日常の作業を通常のユーザーで行います。必要なときだけ、`sudo` で特権のコマンドを実行します。WordPress には、その場だけ権限を上げる同じ操作はありません。アカウントを分けます。

管理者のパスワードが漏れると、被害はサイト全体に広がります。プラグインの追加や、ユーザーの書き換えまでできてしまうためです。毎日開くブラウザには、管理者でログインしたままにしません。

### 7.2. サイト自体を公開する前

サイト全体を初めて公開する前の確認は、記事1本の下書きリンクでは足りません。見る場所は、第6章のローカル環境か、確認用の環境です。本番のアドレスではありません。

見る人は、関係者に限ります。見る対象は、次です。

* ヘッダーとフッター
* 主要ページの文章と画像
* 問い合わせフォームの送信
* 電話番号や、方針ページへのリンク

指摘は、その環境の中で直します。直したコピーを、確認なしに本番に上げません。上げる作業は、第8章の依頼です。

### 7.3. 公開後の、記事を出す前

サイトが公開されたあとも、記事を出す前の確認は残ります。下書きは、訪問者には見えません。確認する人に編集者を渡すと、すべての記事を公開したり消したりできます。たまに見るだけの人には、アカウントを渡さず、期限つきリンクを使います。

道具の候補は、[Public Post Preview](https://ja.wordpress.org/plugins/public-post-preview/) です。下書きのまま、期限つきのリンクを発行します。リンクを知っている人だけが、公開前の見た目を確認できます。

リンクは、見る人だけに渡します。サイト上や、誰でも読める場所には置きません。期限が切れたリンクは、開けなくなります。プラグインの導入が先です。未導入なら、第8章の依頼にします。

流れは、次です。

* 営業スタッフが下書きを書く
* 期限つきリンクを、確認する人に渡す
* 指摘を下書きに反映する
* 公開できる権限の人が、公開する

この流れに、管理者は不要です。公開は、編集者または投稿者が行います。

### 7.4. 混ぜないこと

* サイト全体の公開前確認と、記事1本の公開前確認は、別である
* 下書きリンクを渡すことは、管理者アカウントを渡すことではない
* 毎日のログインを、管理者のままにしない

## 8. 自分で行う作業と、開発者に依頼する作業

移行が終わったあとの目安です。移行の途中は、第9章を優先します。

### 8.1. 営業スタッフが管理画面で行うこと

* 毎日のログインは、管理者以外のアカウントで行う
* 下書きの期限つきリンクを、確認する人に渡す
* 「ダッシュボード」の「更新」を見て、並んでいる項目を開発者に伝える
* 「ニュース」や「お知らせ」の追加と修正
* 「導入事例」「イベント」「採用」「会社情報」の文章と画像の更新
* 固定ページの本文の修正
* 「メディアライブラリ」への画像と PDF の追加
* アドレスを変えない差し替えが必要なとき、開発者に伝える
* サイトエディターでの、ヘッダー、フッター、共通パーツの文言修正
* 試作のアドレスが本番ではないことを確認し、本番に出すかを伝える
* 修正後の表示確認と、「問い合わせ」フォームの送信テスト

送信テストでは、届いたメールと、画面上の完了表示の両方を見ます。

### 8.2. 開発者に依頼すること

「更新」画面に並んだ項目を、本番に反映する作業は、ここに含めます。

* 新しい記事の種類を足すこと
* フォームの送信先、保存先、自動返信を変えること
* 個人情報の取得項目を増やすこと
* 外部サービスや計測タグを足すこと
* WordPress、プラグイン、PHP の更新
* 表示が崩れたときの復旧
* バックアップの設定と、壊れたときの復元
* 復元後に、メディアの登録とファイルがそろっているかの確認
* 画像の圧縮、アドレスを変えない差し替え、SVG をライブラリに出すプラグインの導入
* ローカル環境の作成と、本番とのデータの上げ下げ
* ユーザーの追加と、権限の変更
* 下書きを期限つきリンクで見せるプラグインの導入
* 本番公開と、問題があったときの戻し

依頼するときは、次をセットで伝えます。

* 対象のページ名と URL
* 文言の変更か、並びの変更か、新しい機能か
* 本番に出すか、確認用の環境だけにするか
* 希望日と、確認する人

## 9. 移行が終わるまで

いまの公開サイトは `kix` のままです。`kis2026_base` は作業用であり、ブロックテーマに移し終わったテーマではありません。

この期間は、次を混同しないでください。

* 公開サイトのヘッダーとフッターは、まだテーマのファイル側である
* 「サイトエディターで直せる」という説明は、移行後の話である
* 「イベント」「導入事例」は、まだテーマに依存する部分がある
* 「フォーム」は、保守の止まったプラグインとテーマの組のままである

移行中に、見た目を急いで本番のテーマファイルに足すと、移し替えの差分が増えます。

文言の差し替えは、対象が公開サイトか作業用かを先に分けます。

## 10. 用語

| 用語 | この資料での意味 |
| --- | --- |
| クラシックテーマ | 表示の骨組みを PHP ファイルで持つ方式。公開サイトの `kix` がこれにあたる |
| ブロックテーマ | 表示の骨組みをサイトエディターで扱う方式。移行後の姿 |
| サイトエディター | 管理画面から、テンプレートや共通パーツを編集する画面 |
| テンプレート | トップや記事ページなど、ページ種別ごとの骨組み |
| テンプレートパーツ | ヘッダーやフッターなど、複数ページで共有する部品 |
| パターン | 再利用する塊。「問い合わせ」ボタンの並びなど |
| プラグイン | WordPress に機能を足す部品。フォームや記事の種類を持つ |
| 固定ページ | 「会社情報」のように、日付で流さないページ |
| 投稿 | 「ニュース」のように、日付で積み上がる記事 |
| バックアップ | 壊れた本番を戻すためのコピー |
| ローカル環境 | 自分のパソコンの中で動かす、公開されない WordPress |
| データベース | 記事、設定、フォームの記録が入る入れ物 |
| メディアライブラリ | 画像や PDF の登録一覧。ファイルそのものとは別にある |
| 管理者 | プラグイン、ユーザー、更新までできる権限 |
| 編集者 | 記事の公開はできる。プラグインの追加はできない権限 |
| 下書き | 公開前の記事。サイトの訪問者には見えない |

## 11. 開発者が参照する仕様

役割の境界の正は、次です。

* テーマ側の索引は、[`docs/SPEC.md`](../docs/spec.md) の「依存プラグイン」
* プラグイン群の正は、[「KIS WordPress」の `docs_mod/specs.md`](https://github.com/stein2nd/kis-wordpress/blob/main/docs_mod/specs.md)

移行後、テーマが担当するのは「見た目」です。テンプレート、共通パーツ、パターン、色と文字の共通設定がここに入ります。

記事の種類、問い合わせ、方針ページの台帳は「プラグイン」です。
